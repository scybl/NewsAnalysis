# ValueScope DataHub 项目总规划

本文档用于回答三个问题：这个项目到底做了什么、还有哪些没有做、后续大概要用什么技术和步骤继续做。内容基于当前本地代码与已有文档整理，不等同于服务器实时数据审计结果；服务器实际数据量、任务状态和冷备份进度应以 `chakan` 生成的审计报告和系统治理页为准。

> 历史工程名为 `NewsAnalysis`。当前对外产品名统一为 `ValueScope DataHub`；`ValueScope` 分析是下游消费方。代码包名、服务器目录、MCP 包名和部分冷备份路径暂时保留历史命名，作为兼容层逐步治理。

## 1. 项目定位

| 维度 | 当前定义 |
| --- | --- |
| 项目名称 | ValueScope DataHub |
| 历史工程名 | NewsAnalysis |
| 项目类型 | 面向 A 股研究和个人金融数据治理的数据采集 + 数据中台 + 展示控制台 |
| 核心目标 | 把股票资料包、日 K、分时、财经新闻、冷热存储、数据质量、后台调度、权限安全和数据展示放进一个可部署、可运维的系统，并为下游 ValueScope 分析提供可信数据资产 |
| 当前边界 | DataHub 负责数据采集、存储、治理、展示和健康检查；NewsCrawler 负责新闻采集；ValueScope 分析消费 DataHub 沉淀的数据 |
| 使用场景 | 个人长期维护 A 股数据资产，按需读取冷备份分时数据，查看新闻和行情，监控数据健康，并把整理后的数据交给 ValueScope 分析 |
| 不做什么 | 不做公开交易系统，不做高并发商业 SaaS，暂时不把 Tushare 作为当前新功能默认依赖，不把本仓库定位为主要分析引擎 |

## 2. 总体架构

| 层级 | 已有组件 | 主要职责 | 当前状态 |

| 股票数据层 | `stock_pipeline/stock_storage.py`、`daily_k_coverage.py`、`dossier.py` | 股票资料包、日 K、指标、覆盖索引、存储状态 | 已形成热数据体系，缺口补齐和资料包定期刷新还需增强 |
| 分时冷热层 | `ths_minute.py`、`minute_cold_storage.py`、`minute_storage.py` | 分时抓取、按股票/年份冷归档、百度网盘上传、按需下载缓存 | 已有主链路，正在增强冷备份正确性抽检和差异归因 |
| 新闻采集层 | `NewsCrawler/` | 同花顺、Guardian、Bloomberg、Politico 等新闻采集、去重、健康状态 | 已独立成项目，DataHub 只读展示并供给 ValueScope 分析；部分高反爬源仍需运营级凭据和稳定性增强 |
| 新闻展示层 | `raw_news.py`、`news_library.py`、`news_search.py` | 新闻库检索、股票新闻证据、来源健康展示 | 已可用，后续重点是稳定供给 ValueScope 分析所需的结构化新闻数据 |
| 行情专题层 | `kaipanla.py`、`kaipanla_crawler.py` | 开盘啦功能集成、市场纵览、题材/榜单/连板等行情专题 | 已有抓取、记录、定时和前端展示；部分指标可后续用自有数据重算 |
| 运维治理层 | `ops_status.py`、`data_random_audit.py`、`stock_storage_repair.py` | 任务状态、数据抽检、审计日志、重 IO 保护、股票存储健康检查 | 已有统一系统治理页，后续重点是自动修复闭环和告警 |
| 权限安全层 | `secret_store.py`、`totp.py`、用户/邀请码/API key 管理 | 管理员、只读账号、注册用户、TOTP、加密凭据、审计审批 | 已完成主体能力，后续应加强密钥轮换和操作审计留存 |
| 分析供给层 | `agents/multi_agent.py`、`analysis_frameworks.py`、`deepseek_client.py` | 兼容历史多 Agent 入口、报告读取、下游分析数据供给 | 保留为兼容和验证入口；主线工作应转向数据采集、展示、质量和供给契约 |
| 部署与 CI | Docker Compose、GitHub Actions、`scripts/` | 本地开发、生产部署、安全同步、镜像构建、CI 门禁 | 已有完整雏形，后续可做更稳的蓝绿发布和 worker 化 |

| 权限与安全 | 管理员、只读账号、归档账号、邀请码、TOTP、加密凭据 | `web.py`、`secret_store.py` | 只读账号后端拦截写操作 |

## 6. 技术路线建议

| 方向 | 推荐方案 | 不推荐方案 | 原因 |
| --- | --- | --- | --- |
| 股票日 K 数据源 | Eastmoney/AkShare + 服务器已有 Mongo 数据 + 明确失败记录 | 默认恢复 Tushare | Tushare 当前封存，不能作为新功能前提 |
| 分时历史数据 | `pytdx_history` 抓取 + 百度网盘冷备份 + Mongo 索引 | 全量长期留在服务器 MongoDB | 分时体积大，服务器磁盘压力高 |
| 冷备份验证 | 抽样下载冷对象 + 同日重新抓取 + 分钟级 diff | 只看文件是否存在 | 文件存在不代表当初抓取完整 |
| 新闻采集 | NewsCrawler 独立 Provider + Mongo 契约 | DataHub 或下游 ValueScope 分析直接抓新闻网站 | 保持采集、展示和分析边界清晰，避免主项目再次臃肿 |
| 后台任务 | 任务注册表 + scheduler JSON + 重 IO 互斥 | 裸 `nohup` 分散运行 | 方便前端展示、恢复、审计和避免互相打架 |
| 运维指标 | 系统治理页 + Prometheus/Grafana 可选 | 只靠终端日志 | 页面适合日常巡检，Prometheus 适合长期趋势和告警 |
| 权限安全 | Fernet 密钥库 + TOTP + 后端权限拦截 + 审计 | 把 key 写 `.env` 或前端隐藏按钮 | 前端隐藏不等于权限控制，密钥不能进 Git |
| 前端技术 | 保持原生 HTML/CSS/JS，补静态契约测试 | 立刻重构到大型 SPA | 当前项目核心风险在数据和运维，不在前端框架 |
| 测试策略 | pytest + API smoke + 前端静态契约 + 少量 E2E | 只靠手动点页面 | 后台和数据链路复杂，必须防回归 |
| 发布策略 | `tongbu` 安全同步 + worker 解耦 + 后续蓝绿 | 每次强制重启 | 强制重启容易打断抓取、上传和预取 |

## 7. 里程碑规划

| 阶段 | 目标 | 交付物 | 验收标准 |
| --- | --- | --- | --- |
| M1：数据健康闭环 | 让系统能发现、解释并部分修复数据异常 | 日 K 缺口自动补齐、冷备份差异抽检、股票存储异常工单 | 随机抽检能说明异常原因；可补齐的日 K 自动修复；不可修复的异常可上报 |
| M2：资料包常态更新 | 让每只股票资料包随财报、公告和行情持续刷新 | 资料包刷新 scheduler、刷新记录、失败重试、前端更新时间 | 前端能看到每只股票资料包最新更新时间和刷新结果 |
| M3：数据展示增强 | 从“能查数据”升级到“能看懂数据状态” | 股票数据血缘、新闻结构化标签、冷备份读取状态、质量标记 | 用户能快速判断某只股票有哪些数据、是否完整、能否用于分析 |
| M4：分析供给契约 | 让 DataHub 稳定服务下游 ValueScope 分析 | 数据导出 manifest、资料包版本、新闻证据版本、分析消费记录 | ValueScope 分析可复现每次使用的数据版本和证据来源 |
| M5：运维产品化 | 让系统更像可靠的数据中台 | 告警、审计历史、蓝绿发布、运行手册、前端异常处理工作台 | 主要故障能在系统治理页定位；部署不会随意打断长任务 |
| M6：作品集发布 | 在保护源码和密钥的前提下对外展示项目 | 脱敏公开版、演示数据、架构图、项目说明、截图/视频 | 外部可以看懂数据平台价值，但拿不到生产密钥和完整私有数据 |

## 9. 主要风险与应对

| 风险 | 影响 | 当前已有应对 | 后续建议 |
| --- | --- | --- | --- |
| 数据源变化或反爬 | 抓取失败、数据断层 | 多来源、运行记录、source health | 给每个来源建立失败分类、降级来源和凭据验证 |
| 服务器磁盘不足 | Mongo 或冷备份中断 | 分时冷备份、上传后清理、审计报告 | 冷数据清理自动化，缓存容量硬限制，定期磁盘告警 |
| 部署打断任务 | 分时上传、爬虫、预取失败 | `tongbu` 延迟激活、worker 容器 | 蓝绿发布，任务状态持久化恢复 |
| 冷备份不完整 | 后续分析读到缺失分时 | 索引、sha256、冷备份取回检查 | 抽样重抓比对、差异工单、对象版本修复 |
| Tushare 历史路径误用 | 新功能依赖废弃路径 | 文档和技能中标记封存 | CI 或静态测试禁止新默认路径引入 Tushare |
| 前端状态误导 | 用户以为任务开启或数据完整 | 系统治理页、存储状态页 | 所有状态都显示来源、更新时间和异常原因 |
| 密钥泄漏 | 生产账号和 API key 风险 | 加密密钥库、`.env` 脱敏、CI hygiene | 密钥轮换、过期提醒、公开版仓库脱敏检查 |

## 10. 推荐开发顺序

| 顺序 | 任务 | 预期收益 |
| --- | --- | --- |
| 1 | 完成日 K 缺口自动补齐和失败上报 | 保证基础热数据连续性 |
| 2 | 完成股票资料包定期刷新 | 解决财报季和公告更新后的资料包陈旧问题 |
| 3 | 完善冷备份差异检查的修复闭环 | 让百度网盘冷数据不仅能存，还能证明可用 |

| 5 | 增加 E2E 测试和页面契约测试 | 减少 UI 和接口联动回归 |

| 7 | 建立数据版本和导出契约 | 让 ValueScope 分析可以复现每次使用的数据快照 |

## 11. 一句话总结

这个项目目前已经不是单个爬虫脚本，而是一个围绕 A 股研究数据资产建设的个人数据中台：它的主职责是持续收集、治理、冷备份和展示股票/行情/新闻数据，并把可信数据供给下游 ValueScope 分析；下一阶段最重要的是把“数据是否完整、异常能否自动修复、数据版本能否复现”这三件事做扎实。
